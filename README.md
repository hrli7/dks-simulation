# DKS Simulation

A general research harness for sequential consumer shopping decisions across sporting-goods
and footwear retailers. OpenAI **GPT-6 Luna** generates a reusable bank of shopper traits,
shopping missions, and evidence-grounded retailer descriptions. **Jev** assigns probabilities
to legal actions during each shopping session. A seeded simulator executes those actions,
maintains memory, enforces budgets and time limits, and compares paired store-format scenarios.

This repository contains code, prompts, schemas, tests, and generation scripts. It contains
**no historical experiment results, private merchandise data, saved shopper traces, or API keys**.
Generated inputs and outputs belong in `data/` and are ignored by Git.

## Setup

Use Python 3.11 or later. Run commands from the repository root.

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
```

Supply `OPENAI_API_KEY` and `TYPESAFE_API_KEY` as environment variables through your
shell or secret manager. `.env.example` lists names only. The Luna generator reads the process
environment; the Jev client additionally supports a local, ignored `.env` file.
Never paste credentials into code, evidence, prompts, or committed configuration.

Generation uses the OpenAI Responses API with `gpt-6-luna` and strict JSON schemas.
The decision engine defaults to `jev-1.13.0`. Provider access to these models is required;
there is no silent fallback. A `--model` override is available for input generation.

## Pipeline

1. Collect sourced retailer facts and authorized product observations.
2. Generate and freeze Luna-authored shopper options and retailer descriptions.
3. Compose reproducible individual profiles from the frozen option bank and a seed.
4. Prepare the same consumers and merchandise for baseline, HoS, FastBreak, and combined scenarios.
5. Run sequential Jev decisions with independent session state and common seeded draws.
6. Replay the saved API responses without network access and summarize paired outcomes.

### 1. Prepare evidence and merchandise

Create `data/private/retailer_evidence.json`. It maps every profile ID in
`generate_inputs.BANNERS` and `generate_inputs.FORMATS` to an object with:

```json
{
  "dks": {
    "facts": ["Insert verified merchandise and service facts here."],
    "sources": ["https://example.com/replace-with-an-actual-source"]
  }
}
```

The fragment above demonstrates the schema; it is not sufficient evidence for a run.
Include all banner/format IDs. Evidence should describe assortment, services, merchandise
presentation, relevant private-brand ownership, and limitations. Keep hypothetical scenario
features explicitly labeled. Luna receives the supplied facts; it does **not** independently
browse or verify source URLs. Review generated descriptions before preparing an experiment.
Do not provide desired revenue uplift or prior results as generation context.

Create `data/private/offers.jsonl`, one normalized product observation per line. Required fields:

| Field | Meaning |
|---|---|
| `retailer` | Exact catalog banner name from `generate_inputs.BANNERS` |
| `name`, `category` | Product name and retrieval category |
| `price`, `currency` | Positive item price; this harness supports USD |
| `family` | `historical_variant`, `competitor_offer`, or `launch_listing` |
| `observed_at` | ISO date or timestamp at or before the snapshot cutoff |

Also supply `brand`, `size`, `gender`, `color`, `availability`, `source_url`,
`product_key`, and `gtin14` when observed. `observation_id` can be supplied or is derived
from the row hash. Categories supported by shopper missions are `footwear`, `cleats`,
`clothing`, `basketball`, `golf_ball`, `golf_bag`, and `golf_driver`.
Use `web_buyable` or `https://schema.org/InStock` only when supported by the observation.
Unknown size/availability remains unknown until explicitly simulated; launch listings are
not proof of in-stock inventory. Do not generate fictional merchandise for a research run.
The importer expects a preselected snapshot, not a full multi-date price history.

```bash
python catalog_io.py --input data/private/offers.jsonl \
  --output data/catalog.sqlite --as-of YYYY-MM-DD
```

Replace `YYYY-MM-DD` with your actual evidence cutoff. The engine can alternatively consume
an existing compatible SQLite snapshot with the same columns and metadata.

### 2. Generate inputs with Luna

```bash
python generate_inputs.py --model gpt-6-luna \
  --evidence data/private/retailer_evidence.json \
  --options-per-trait 25 --output data/generated
```

This makes separate requests for ten behavioral categories, shopping missions, and each
retailer profile. The default requests 250 behavioral options plus shopping missions;
numerical budget/time/size grids are generated by code. Compatibility tags restrict the
options available to each mission. Private-brand descriptions are generated only from
supplied ownership evidence. All prompts and JSON schemas are in `generate_inputs.py`.

Outputs include `option_bank.json`, `retailer_profiles.json`, `manifest.json`, and
`generation_cache/`. Partial generation can resume from its request cache. Once final files
exist, choose a new output directory to generate another version. API generation may incur
charges. A seed cannot guarantee identical fresh LLM outputs; retain the frozen files.

### 3. Prepare a paired experiment

```bash
python simulate.py prepare --run data/runs/example-001 \
  --inputs data/generated --catalog data/catalog.sqlite \
  --count 2000 --seed example-001
```

`--count` counts consumers across both channels. Each consumer receives all four scenarios;
physical-only metrics are reported separately. Profiles are saved individually within prepared
sessions and together under `cohort/`. Preparation freezes retailer contexts, merchandise
selection, profile options, access times, source snapshots, and hashes. It refuses to overwrite
an existing run. The seed determines option selection and common random draws, not a
representative population distribution.

### 4. Run and resume Jev sessions

```bash
python simulate.py run --run data/runs/example-001 --workers 8
```

Workers use local threads for concurrent API requests. Repeating this command resumes missing
episodes and reuses cached requests. Increase concurrency only within your provider limits.
This version does not require Modal and does not claim to reproduce a distributed deployment.

Each decision supplies the shopper mission and preferences, remaining time, basket and total,
current retailer context, discovered offers, revealed availability/fit, recent history, and
legal actions. Actions include visiting a retailer, browsing, checking availability, trying
an item, exploring an activity, adding/removing an item, switching stores, checking out,
and ending without a purchase. Jev returns action probabilities, not a fabricated dialogue.

### 5. Replay and analyze

```bash
python simulate.py replay --run data/runs/example-001
python simulate.py analyze --run data/runs/example-001
```

Replay recomputes full episodes from cached Jev responses and compares every saved field.
A cache miss fails without network access. Analysis requires all paired episodes and writes
`analysis.json`, including entrants, buyers, conversion, ticket, revenue per occasion,
units per ticket, censoring, and paired revenue differences with descriptive intervals.
Zero-denominator metrics are null. Online controls must match across physical-format scenarios.
The analysis files remain local under the ignored `data/` directory.

## Offline smoke test

This generates tiny **mechanical fixtures**, without LLM-authored personalities or API calls.
The catalog deliberately gives every banner the same fictional shoes. The policy chooses
legal actions deterministically. Its outputs are useful only for checking the software.

```bash
python generate_inputs.py --demo --output data/demo-inputs
python catalog_io.py --demo --input data/demo-offers.jsonl \
  --output data/demo.sqlite --as-of 2000-01-01
python simulate.py prepare --run data/runs/smoke \
  --inputs data/demo-inputs --catalog data/demo.sqlite --count 8 --seed smoke
python simulate.py run --run data/runs/smoke --demo --workers 2
python simulate.py replay --run data/runs/smoke
python simulate.py analyze --run data/runs/smoke
```

Use new directory names for another smoke run. Demo and Jev episodes cannot be mixed.

## Reproducibility and interpretation

The published repo reproduces the **method**, not undisclosed historical numbers. Exact replay
requires the original frozen inputs, source version, and API caches, which are deliberately
excluded. Reformatting changes source hashes; prepare a fresh run after changing code.
Luna input regeneration creates a new experiment. Provider model behavior may change; saved
responses are the authoritative replay record.

Current explicit assumptions include uniform sampling within compatible trait lists, hypothetical
5–25 minute physical access, 75% seeded availability when unknown, 80% seeded trial suitability,
8% tax for budget enforcement, zero shipping, and a 24-action cap. Products are heuristically
ranked and paginated. All listed banners are hypothetically accessible. These are scenario
parameters, not calibrated empirical estimates. Physical format scenarios preserve merchandise
and prices; FastBreak adds optional apparel visibility, and HoS adds activity/testing context.

One consumer represents one shopping occasion. The engine does not model population-weighted
catchments, generated trips, repeat visits, annual omnichannel store sales, or actual floor plans.
A successful replay validates execution, not realism. Validate against held-out human choices,
observed traffic/conversion/tickets, assortment coverage, and independent store evidence before
using outputs as investment evidence. Report unfavorable outcomes and avoid tuning to a desired
retailer uplift. Paired intervals describe variation within the constructed cohort only.

## Development and repository hygiene

```bash
ruff check .
ruff format --check .
python -m unittest discover -v
python check_repository.py
```

Tests cover profile determinism, session isolation, budget and time guards, action legality,
paired latent outcomes, online controls, API cache behavior, generation schemas, and an offline
end-to-end run. `check_repository.py` scans tracked files for credential patterns and forbidden
data paths. It complements a dedicated secret scanner; it is not a guarantee against every
possible secret format. CI runs offline and needs no credentials.

Key files: `generate_inputs.py` (Luna generation and schemas), `generate_shoppers.py`
(seeded profiles), `catalog_io.py` (catalog import/fixtures), `catalog_swarm.py` (world and Jev
policy), `jev_client.py` (API and cache), `simulate.py` (orchestration/replay/analysis),
`retailer_profiles.py` (context projection), and `metrics.py` (metric definitions).

API references: [OpenAI GPT-6 Luna](https://developers.openai.com/api/docs/models/gpt-6-luna),
[Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs),
[TypeSafe Jev introduction](https://typesafe.ai/blog/introducing-system-one-models-and-jev).
